# 실험 2: 평가 방법 다시 세우기 (2026-11-06)

## 계기

- 목표는 수업 우승. 최종 상대는 baseline이 아니라 다른 학생들의 에이전트임.
- 조교 제공 PPO가 강하고 제출 예제까지 있어서, 다른 학생들도 상당수 이 체크포인트에서 출발할 가능성이 높음. 그래서 원본 PPO를 확실히 이기는지가 가장 중요한 기준.
- 한쪽에 치우친 에이전트는 안 됨. TradeBuilding, ActionValue만 이기도록 학습하면 다른 스타일의 상대에게 약해질 수 있음.

## 전체 baseline과 원본 PPO의 승률 (docs/BASELINES.md, 조교 측정)

| 상대 | 종류 | 원본 PPO 승률 |
|---|---|---|
| Random | 무작위 | 100% |
| Factory | 규칙 기반 | 거의 100% |
| ShippingRush | 규칙 기반 | 100% |
| TradeBuilding | 규칙 기반 | 약 90% (우리 1000판 측정) |
| ActionValue | 규칙 기반 | 약 89% (우리 1000판 측정) |
| MCTS | 탐색 | 90% |
| SearchLite | 탐색 | 45% |
| Search | 탐색 | 39% (160판) |

- 진짜 강적은 TradeBuilding, ActionValue가 아니라 SearchLite, Search였음. 원본 PPO는 이 둘에게 지고 있음.
- MCTS, SearchLite, Search는 한 수에 최대 1초를 써서 느림.

## 원본 PPO와 직접 대결: 43%가 나온 이유

- play.py로 Moka vs 원본 PPO 200판 (시드 10000): 85승 114패 1무, 43%.
- 두 에이전트는 가중치가 같아서 50%가 나와야 할 것 같았음.
- 확인: 같은 시드에서 좌석만 바꿔 20판씩 둬 보니 20판 모두 이긴 좌석과 점수가 같았음. 즉 둘은 항상 같은 수를 둠.
- 원인: play.py는 판마다 시드를 바꾸면서 좌석을 번갈아 앉음. 같은 실력끼리 두면 승패가 그 판에서 어느 좌석이 유리했는지로 정해짐. 43%는 좌석 운이 50% 근처에서 흔들린 값.

## 측정 도구 변경: course_ladder.py

- 저장소에 조교가 실제 래더를 돌릴 때 쓰는 tools/course_ladder.py가 있음.
- play.py와 다른 점
  - 같은 시드를 좌석을 바꿔 두 번 둠. 좌석 운이 상쇄돼서 같은 에이전트끼리는 정확히 50%가 나옴. 시험 삼아 Moka vs 원본 PPO 10개 시드 x 좌석 교대로 둬 보니 10승 10패.
  - 실제 대회처럼 에이전트를 격리된 프로세스에서 실행함.
  - 여러 판을 동시에 둬서 Search 같은 느린 상대도 빨리 끝남.
- 사용법: results/entries/ 아래에 대회 제출 형식(학번_이름 폴더에 my_agent.py, weights.pt)으로 버전마다 폴더를 만들면, 우리 버전들끼리도 좌석 교대로 대결시켜 순위표를 만들어 줌.

## 새 평가 기준

| 구분 | 측정 | 의미 |
|---|---|---|
| 공격 | 원본 PPO와 직접 대결 | 같은 출발점의 학생들을 이길 수 있는가 (가장 중요) |
| 미드필드 | TradeBuilding, ActionValue, SearchLite, Search | 다른 스타일과 강한 상대에게 무너지지 않는가 |
| 수비 | Random, Factory, ShippingRush, MCTS / 시간 초과, 불법 행동 0 | 쉬운 상대에게 지지 않고, 규칙 위반으로 공짜 실점을 내주지 않는가 |

- 측정: course_ladder.py, 시드 10000-10099 (상대마다 100개 x 좌석 교대 = 200판)
- 좋은 후보 최종 확인: 시드 20000번대 (자주 쓰지 않음)
- 채택 기준: 아래 세 가지를 모두 만족할 때만 새 버전을 채택함
  1. 원본 PPO와의 직접 대결에서 50%를 확실히 넘음
  2. baseline 상대 승률이 떨어지지 않음
  3. 시간 초과, 불법 행동 0

## 학습 상대에 baseline을 섞는 것이 치팅인지 확인

- 치팅 아님으로 판단. 근거:
  1. 조교 예제(examples/ppo_entry/my_agent.py) 설명에 "fine-tuning the weights against the baselines that beat it"이라고 직접 적혀 있음.
  2. 금지 항목은 제출한 에이전트가 대전 중에 하는 일에 대한 것. 학습은 제출 전 개발 과정이고, baseline 코드는 제출물에 들어가지 않음.
  3. baseline은 다른 학생 코드가 아니라 조교가 제공한 저장소 모듈이고, 저장소 모듈 사용은 허용됨.
- 다만 baseline에만 맞춰지지 않도록 self-play와 섞어서 학습할 예정.

## 기준선 측정 (exp00)
 
- 명령: course_ladder.py --entries results/entries --label exp00 --seeds 10000-10099, baseline 8종 전부
- 결과 (2026-11-06, 141분 소요, 8판 동시 실행):
| 상대 | 승수 | 승률 |
|---|---|---|
| Random | 200 / 200 | 100% |
| ShippingRush | 197 / 200 | 98.5% |
| Factory | 191 / 200 | 95.5% |
| MCTS | 183 / 200 | 91.5% |
| TradeBuilding | 178 / 200 | 89% |
| ActionValue | 178 / 200 | 89% |
| SearchLite | 66 / 200 | 33% |
| Search | 65 / 200 | 32.5% |
| 전체 | 1258 / 1600 | 78.6% |
 
- 시간 초과 0, 불법 행동 0, 상태 변경 0. 8판 동시 실행의 무거운 조건에서도 규칙 위반 없음.
- TradeBuilding, ActionValue 89%는 play.py 1000판 결과와 거의 같음. 도구와 시드가 달라도 같은 값이라 믿을 만함.
- 규칙 기반 봇에게는 89~100%로 이기지만, 탐색 봇인 SearchLite, Search에게는 3판 중 2판을 짐. 조교 측정(45%, 39%)보다 낮은데, 조교 측정은 40~160판이라 200판인 이 값이 더 정확하다고 봄.
- 가장 크게 올려야 할 곳은 TradeBuilding, ActionValue의 10%가 아니라 탐색 봇 상대 33%.
- Search는 한 판에 1분 가까이 걸려서 학습 상대로는 쓸 수 없음. 그래서 1단계는 빠른 baseline과 self-play를 섞은 추가 학습, 2단계는 act()에 미리 두어 보기를 결합하는 방향으로 계획함.
