# act() 안 탐색 2차: 정책으로 줄이고 상대는 최악으로 (2026-11-27)

## 왜 다시 했나

- 래더 3에서 19명 중 10위로 내려감 (L3). 위쪽 학생들 이름에 탐색을 뜻하는 말이 보이고, Moka는 한 수에 제한 시간의 1%만 씀.
- Z 문서에서 "다음에 할 것"으로 넘긴 탐색 2차를 학습 대신 다시 꺼냄. 학습은 하루 반이 걸리지만, 탐색은 이미 있는 v8 신경망으로 바로 시험할 수 있음.
- S1의 실패 원인: 상대도 우리 정책대로 둔다고 가정한 롤아웃 → 다르게 두는 상대(ActionValue)에게 92% → 51%.

## 방법

- 내 차례 마디: 정책 확률 상위 3수만 펼침. 상대 차례 마디: 같은 신경망으로 상대 입장에서 본 정책 상위 3수를 펼치되, 그중 **나에게 가장 나쁜 수**를 고른다고 봄 (상대를 한 수로 가정하지 않음).
- 마디 값: 가치 신경망 (게임 끝 보상이 이기면 +1, 지면 -1이라 값은 대략 "2 × 승률 - 1"). 상대 차례면 부호를 뒤집어 내 입장으로.
- 한 층의 마디를 모아 신경망에 한 번에 넣음 (1개 6.9 ms → 9개 묶음 1.0 ms, 27개 1.9 ms).
- 3수 앞까지 봄. 층마다 결론을 저장하고 30 ms가 넘치면 끝까지 계산한 층의 결론을 씀.
- 탐색 결과가 정책 1순위보다 0.05 넘게 좋을 때만 바꿈. 1순위 확률 0.95 이상이면 탐색하지 않음.
- 숨겨진 농장 순서는 forward model의 clone()이 섞어 줌. 실제 게임 상태는 건드리지 않음.

## 시간 초과 문제와 해결

- 처음 버전은 작업 공간(CPU 2개, 동시에 2판)에서 시간 초과가 남 (3수 13번, 4수 492번 / 2000판).
- 혼자 둬도 한 수 최대 95~112 ms. 느린 수를 프로파일해 보니 복사(deepcopy) 한 번이 70 ms 걸림 = Python의 순환 참조 정리(gc)가 탐색 도중에 일어난 것.
- 탐색하는 동안만 gc를 멈추고 끝나면 되돌림. 층마다 시간 확인을 더 촘촘히 하고, 시간이 넘치면 마지막으로 끝난 층의 결론을 쓰게 바꿈.
- 결과: 3수 버전 한 수 평균 11 ms, p99 20 ms, 최대 24 ms (혼자, 스레드 1개). validate_submission READY (실패 0, 경고 0).

## 시간 초과 원인 확인 (작업 공간)

- 기록 파일에는 시간 초과 수가 판마다 남지 않아서 어느 상대와의 판에서 났는지는 모름.
- 가설 1: Python의 전체 메모리 정리(gc gen2). 에이전트 프로세스에는 torch 등의 객체가 약 19만 개 있어서 전체 정리 한 번에 혼자서도 60~80 ms가 걸림. gc.freeze()로 이 객체들을 정리 대상에서 빼면 0 ms가 되고, 두는 수는 그대로 (10판 1505수 중 차이 0).
- 확인: 공식 sandbox로 둬서 에이전트 안에서 gc가 일어난 횟수를 셈. 3.13 기준(정리 기준값 2000)으로 200판 32,105수, 노트북과 같은 3.12 기준(700)으로 100판 약 15,700수에서 전체 정리는 0번 (부분 정리만 수십 번, 가장 길어야 약 4 ms).
- 가설 1은 철회함. 전체 정리는 너무 드물어서 73번의 원인이 될 수 없음. gc.freeze()는 넣지 않음.
- 실제로 본 것: 부하가 없는 sandbox에서도 한 수 왕복이 50~58 ms까지 가는 수가 있음 (100판 중 5수). 두 가지가 섞여 있었음.
  - 에이전트 안: 탐색이 30 ms에서 멈추지 못하고, 마지막으로 하던 계산(복사, 관찰 만들기, 신경망 묶음) 하나를 끝내느라 54.7 ms까지 감.
  - 에이전트 밖: 에이전트 안은 30 ms 안에 끝났는데 왕복이 50 ms를 넘음. 상태를 넘겨받는 부분(forward model 스냅샷 전달)에서 20 ms 안팎이 더해짐.
- 노트북에서 여러 판이 동시에 돌면 두 가지 모두 늘어나 100 ms를 넘는 것으로 봄. baseline 측정은 Search·MCTS가 같이 돌아 부하가 가장 컸음.
- 작업 공간 sandbox 100판에서 부하 없이 시간 초과가 1번 남. 원인은 찾지 못함 (그 수의 기록이 남지 않음).
- 채점 환경은 64코어 컴퓨터에서 32판 동시이고, 조교 측정으로 한 수 시간이 약 10% 늘어나는 정도 (수업 문서). 노트북(12스레드에서 8판, 판마다 프로세스 2개)보다 훨씬 여유가 있음. 래더 1~3에서 Moka(탐색 없음)는 시간 초과 0번.

## MokaB: 예산을 act() 시작부터 20 ms로 (2026-11-27 밤)

- 목적: 가장 긴 수를 줄여 시간 초과를 줄일 수 있나. 바꾼 것은 하나. 예산을 탐색 시작이 아니라 act() 시작부터 세고, 30 ms → 20 ms.
- 작업 공간: 10판에서 MokaS와 두는 수가 하나도 다르지 않음 (1505수). 한 수 최대 29.5 ms. validate READY.
- 노트북: 엔트리 MokaS, MokaB(results/entries_s2b/1502_b20), P6. 시드 50000-50499를 125개씩 4묶음 (results/ladder/s2b_1 ~ 4), 터미널 4개, 각 --workers 2 (8판 동시, 40000번대 확인과 같은 부하). 묶음마다 약 30분.

| (시드 50000번대, 1000판) | MokaS | MokaB |
|---|---|---|
| 맞대결 | 49.6% | 50.3% |
| P6 상대 | 87.1% | 85.0% |
| 시간 초과 (2000판) | 8 (2 / 2 / 2 / 2) | 5 (1 / 1 / 2 / 1) |

- 맞대결 50.3%로 같은 실력.
- P6 상대는 MokaB가 2.1%p 낮음. 차이의 표준오차(약 1.5%p) 안이라 떨어졌다고는 할 수 없지만 나아지지도 않음.
- 시간 초과 8번 대 5번은 우연으로도 나올 수 있는 차이.
- MokaS의 P6 상대 87.1%는 40000번대(87.2%)와 거의 같음. 시드를 바꿔도 탐색의 이득이 그대로 나옴.
- 판정: MokaB는 채택하지 않음. 바꿀 이유가 되는 숫자가 없음. 예산을 줄여도 시간 초과가 크게 줄지 않으므로, 시간 초과는 탐색 예산보다 노트북 부하 자체의 영향이 크다고 봄.
